# Отчёт тестировщика — ActivityHeatmap (native)

Тестировался только `native/`. Прототип `../ubersicht-prototype/` не открывался и не анализировался
(за исключением того, что `--self-test` сам запускает его `aggregate.py` как вторую реализацию
для кросс-валидации — это чужая работа, не моя, и не разбиралась).

Методология: код читался, но каждая находка ниже либо воспроизведена живым прогоном бинарника
против реальных `~/Library/Application Support/ActivityHeatmap/*.json` (с бэкапом/восстановлением
по чек-сумме), либо подтверждена независимым SQL-запросом к копии `knowledgeC.db`, либо
воспроизведена синтетикой, повторяющей алгоритм 1:1 (сверено построчно с исходником).

## Воспроизводимые баги

### 1. Повреждённый `activity.json` не просто «переживается» — он тихо теряет историю, которой нет в живой базе (Приоритет A, критично)

**Что сделал.** Скопировал реальные `activity.json`/`catalog.json` (сверил SHA-256). Взял копию
`activity.json`, добавил в неё синтетический день `"2026-05-01"` (в пределах 91-дневного
горизонта, но заведомо вне окна, которое сейчас видно в `knowledgeC.db` — там сейчас данные
только 2026-07-13…21). Прогнал этот вариант через реальный бинарник (`./.build/debug/ActivityHeatmap`,
без флагов, обычный `applicationDidFinishLaunching` → `refresh()`) — день пережил цикл, как и
ожидалось (контрольный прогон, поведение верное).

Затем **обрезал** тот же файл посередине (сделал невалидный JSON, имитация обрыва при краше) и
повторил прогон. Отдельно проверил и пустой файл (0 байт).

**Ожидал.** По ARCHITECTURE.md / брифу: «При любой ошибке чтения файл не перезаписывается» —
единственная копия истории, которую macOS уже удалила из своей БД.

**Получил.** Приложение не падает и не подставляет дефолты — но и не оставляет файл в покое.
После обрезанного (и после пустого) `activity.json` файл **тихо перезаписывается** результатом
свежего скана `knowledgeC.db`, и день `"2026-05-01"`, существовавший только в истории, **исчезает
без единой записи в лог** (в `activity.log` для этого пути вообще нет строки — ни ошибки, ни
предупреждения).

**Механизм (код, `Data/Store.swift`):**

```swift
func loadPrevious() -> [String: DayStats] {
    guard let data = try? Data(contentsOf: url) else { return [:] }
    guard let snapshot = try? JSONDecoder().decode(ActivitySnapshot.self, from: data) else { return [:] }
    return snapshot.days
}
```

`mergeHistory` зовёт `loadPrevious()` **внутри** успешного `refresh()` — то есть после того, как
чтение `knowledgeC.db` уже прошло без ошибок. Если предыдущий `activity.json` не парсится,
`loadPrevious()` молча возвращает `[:]` — то же самое, что «файла никогда не было». Дальше
`mergeHistory` берёт `fresh` (только дни, видимые в текущем скане БД) и пишет их как новую
историю. Правило «при ошибке чтения не перезаписывать» защищает только путь «БД недоступна»
(`Knowledge.loadRows` бросает → `refresh()` выходит по `try` до `write()` — это действительно
работает, проверено тем же способом, см. ниже). Оно **не** защищает путь «предыдущий
`activity.json` повреждён, а БД читается нормально» — а именно в этом случае файл и нужен
больше всего: он единственный источник дней, которых уже нет в живой БД (по STATUS.md, БД
на машине разработки держит порядка 6 дней).

**Итог:** любое повреждение `activity.json` — не только злонамеренное, но и обрыв записи при
краше в неудачный момент, конфликт синхронизации, ручное редактирование, диск-глюк — на
следующем же успешном цикле (а он раз в час и один раз при каждом старте) **необратимо** режет
накопленную историю до того, что прямо сейчас видно в Screen Time. 91-дневное окно превращается
в 6–9-дневное, без единого сигнала пользователю или в лог.

**Восстановление реальных данных подтверждено:** после каждого из трёх прогонов (валидный+день,
обрезанный, пустой) исходные `activity.json`/`catalog.json` восстанавливались из бэкапа и
сверялись по SHA-256 (полное совпадение). Финальная проверка в конце сессии: 8 из 9 реальных
дней (13–20 июля) байт-в-байт совпадают с бэкапом; день 21 июля (сегодняшний, ещё копится)
закономерно немного вырос — это уже легитимная работа приложения после восстановления, не потеря.

**Замечание:** для сравнения тем же способом проверил путь «БД недоступна»
(`store.refresh(dbPath: "/nonexistent")` — это и так покрыто `StoreTests.swift`,
`testFailedRefreshDoesNotTouchExistingFile`) — там файл действительно не трогается, это
работает. Дыра именно в паре «файл истории повреждён, но БД в порядке» — сценарий, для
которого в `StoreTests.swift` теста нет вообще.

## Подозрения (не удалось наблюдать на реальных данных, но код+синтетика указывают на баг)

### 2. Кросс-браузерное «заражение» времени домена (Приоритет B, свежая функция баланса)

**Как заметил.** Читая `Aggregator.collect()`, в месте, которое отвечает за правило 4
(«время домена = его интервалы ∩ интервалы `/app/usage` **его** браузера»):

```swift
let browserTime = Intervals.merge((foreground[day] ?? [:]).values.flatMap { $0 })
for (key, iv) in perWeb[day] ?? [:] {
    scored[key] = Intervals.awakeDuration(Intervals.intersect(iv, browserTime), holes)
}
```

`perWeb` ключуется только доменом — привязка «этот webUsage-интервал пришёл именно от Safari»
теряется на входе (`perWeb[piece.day, default: [:]][key, ...]`, `key` = домен, не браузер).
`browserTime` — это `merge` **по всем** браузерам сразу (`foreground[day]?.values.flatMap`), не
именно того браузера, который открывал домен. Значит, если пользователь в один день пользуется
двумя браузерами, время домена A (открытого в браузере 1, но оставленного в фоне) может
засчитаться, пока на переднем плане именно браузер 2 — хотя браузер 1 в этот момент вообще не
активен.

**Подтверждение синтетикой** (повторил `Intervals.merge`/`intersect` 1:1 по исходнику,
`/private/tmp/.../scratchpad/sim.py`): Safari на переднем плане 09:00–10:00 с открытым
excalidraw.com (полезное), Chrome на переднем плане 10:00–11:00 с youtube.com (вредное);
excalidraw-вкладка простояла открытой весь час 09:00–11:00.

| | ожидаемо (по ARCHITECTURE.md, «его браузера») | фактически (код как есть) |
|---|---|---|
| excalidraw.com | 09:00–10:00 = 1ч | 09:00–11:00 = **2ч** |
| youtube.com | 10:00–11:00 = 1ч | 10:00–11:00 = 1ч |
| баланс дня | 0 | **+1ч** |

**Реальные данные:** в каталоге пользователя (`catalog.json`) присутствуют и Safari
(71706 сек. накоплено), и Chrome (1516 сек.) — то есть оба браузера реально использовались.
Но прямой SQL-проверкой `knowledgeC.db` подтвердил: `webUsage`-строки за все 9 дней истории
шлёт **только Safari** (Chrome не генерирует `/app/webUsage` вовсе — вероятно, из-за
настроек интеграции со Screen Time). Значит на текущих данных бага не видно (только один
браузер попадает во множество `browsers`), но код к этому не готов: в момент, когда Chrome
начнёт слать webUsage (обновление ОС, включение разрешения, или просто у другого
пользователя this build), баланс конкретных дней начнёт искажаться без предупреждения — это
не то же самое, что уже известная дыра C2 («вкладки считаются дважды» — там переучитывается
время **внутри одного и того же** браузера; здесь конкретный домен может получить время
**чужого** браузера).

**Что не смог:** заставить Chrome реально сгенерировать `webUsage`-записи на этой машине,
чтобы подтвердить на живых данных — это требует изменения системных настроек интеграции
Screen Time с браузером, вне границ задачи.

## Измерено (известные дыры — не баг, но масштаб на реальных данных)

### 3. C2 «параллельные вкладки» — реально проявляется, конкретный день

Проверил инвариант `useful + destructive ≤ t` по всем 9 реальным дням в `activity.json`.
На **2026-07-15** он нарушен:

```
t = 15025s (4ч10м)     useful = 14002s     destructive = 4907s
useful + destructive = 18909s (5ч15м)  →  на 3884с (65 минут, ~26%) больше отслеженного дня
```

Превышение приходит не из топ-3 дня (их суммы разумны), а из совокупности прочих
одновременно открытых вкладок/доменов вне топ-3, каждая из которых независимо пересекается с
временем своего браузера на переднем плане. На остальных 8 днях инвариант не нарушен
(`useful+destructive` заметно меньше `t` везде), так что 15 июля — не типичный день, а именно
тот случай, который бриф просил поискать: «бывают ли дни, где это заметно искажает картину» —
да, бывают, и это не редкость по масштабу (более чем на час, четверть дня).

### 4. Запись-монстр `desktop.docker.com` (46 часов) — обрезается правильно

Нашёл ту же запись, что упомянута в брифе, прямым SQL к копии БД: `desktop.docker.com`,
2026-07-13 23:45:39 → 2026-07-15 21:43:02, 45.96 часа одной строкой (закреплённая вкладка).
Пересчитал вручную (тот же алгоритм: пересечение с реальными интервалами `/app/usage` для
`com.apple.Safari` за это окно, минус блокировки — блокировок в этом окне не было): пересечение
даёт **4.81 часа**. В `activity.json` эта запись размазана по дням (14 июля: 11120с = 3.09ч,
15 июля: 6001с = 1.67ч, сумма близка к пересчитанной величине с учётом разбиения по суткам) —
обрезка работает так, как описано в ARCHITECTURE.md. Других записей длиннее 3 часов в
`/app/usage`/`/app/webUsage` за всё видимое окно БД не нашлось (проверено SQL-запросом по
всем строкам).

### 5. Кросс-девайсная фильтрация (`ZSOURCE.ZDEVICEID`) — подтверждена работающей на живых данных

Прямой SQL к копии `knowledgeC.db`: все строки `/app/usage` (6808) и `/app/webUsage` (5941)
имеют `ZSOURCE IS NULL` (локальные), все 554 строки `/device/isLocked` со значением 1
принадлежат одному и тому же удалённому `ZDEVICEID` (`EF5AF00E-...` — тот же айфон, что
упомянут в ARCHITECTURE.md) и корректно отфильтровываются. Каталог (`collectCatalog`)
использует те же уже отфильтрованные `usage`/`locked` массивы, что и `collect()` — отдельного
незащищённого запроса для каталога нет, так что «заразы» именно там я не нашёл. В каталоге нет
явно айфонных бандл-id (`com.apple.MobileSMS` — это настоящий бандл-id Mac-приложения
«Сообщения», не утечка).

**Не до конца проверено:** таблица `ZSOURCE` содержит помимо двух настоящих `ZDEVICEID` ещё
одну группу строк (69 шт.) с **пустой строкой** `ZDEVICEID` (не `NULL`). Фильтр в коде
(`... IS NULL`) отличает `NULL` от `''` — пустая строка не пройдёт как «локальная». Сейчас
ни одна строка `ZOBJECT` из интересующих потоков не ссылается на эти 69 строк `ZSOURCE`
(проверено JOIN'ом, результат пуст), так что на практике сейчас это не проявляется. Не смог
определить, что это за 69 строк и при каких условиях они могли бы получить ссылку — это
осталось предположением, не багом.

### 6. Устойчивость к смене часового пояса / переходу на летнее время — проверено переносом алгоритма, не на этой машине

Машина использует `Europe/Minsk` (фиксированный +03, без перевода стрелок) — живой переход
через DST на ней не воспроизвести без смены системного часового пояса, а это уже «изменение
системных настроек», выходит за рамки того, что разрешено делать агенту. Вместо этого
скопировал `Aggregator.splitByDay` дословно в отдельный swift-скрипт и прогнал с
`Calendar`, у которой `timeZone = America/New_York`, через оба перехода 2026 года (весенний
07.03→08.03, осенний 01.11). Результат корректный: `Calendar.startOfDay`/`date(byAdding: .day)`
в Foundation учитывают DST на уровне абсолютного времени — интервал в 5 часов по настенным
часам, пересекающий скачок стрелки вперёд, даёт ровно 4 часа реального времени и именно так
и разбивается на куски. Бага не нашёл, но это проверка алгоритма в изоляции, а не прогон
самого скомпилированного бинарника — см. «не смог проверить».

## Что проверить не смог

1. **Пункт D брифа целиком** (перетаскивание живой рукой, ручка масштаба, тумблер «Запускать
   при входе», кнопка «Открыть настройки системы», иконка в Dock/Finder, `build.sh release`) —
   как и предупреждал бриф, это требует живого человека за мышью/клавиатурой или реальных
   системных side-эффектов (Login Item, TCC-диалоги), которые агенту трогать нельзя. Осталось
   непроверенным, как и зафиксировано в STATUS.md.

2. **Гонка записи двух экземпляров** (пункт A брифа). Во время тестирования выяснилось, что уже
   был запущен один экземпляр реального `.app`-бандла (не мной — существовал до начала сессии),
   и параллельно с ним я на несколько минут поднимал свои тестовые запуски бинарника. Реального
   одновременного попадания в `write()` не зафиксировал (таймер обновления — раз в час, мои
   инстансы просто writes на старте, не совпадали по секунде) — так что «кто выиграет гонку»
   не пронаблюдал напрямую. По коду `FileManager.replaceItem` — атомарная POSIX-операция, так
   что *в худшем случае* ожидаю «выигрывает последний записавший» без порчи файла, но это вывод
   из чтения кода, а не наблюдение гонки.

3. **DST/смена часового пояса на самом бинарнике** — см. находку 6 выше: проверено переносом
   алгоритма на отдельном скрипте, не самим приложением, потому что смена системного часового
   пояса на машине — это изменение системных настроек.

4. **Кросс-браузерная утечка (находка 2) на реальных данных** — не смог заставить Chrome
   генерировать `/app/webUsage` на этой машине; подтверждено только синтетикой, повторяющей
   алгоритм.

5. **Раздел F (интерфейс)** почти не тронут — не хватило времени после находок по A/B/E.
   Не проверял: прокрутку окна настроек, переключение языка на лету, масштаб 50–150% на живом
   виджете, тёмную тему, обои разных цветов. Также не переоткрывал то, что уже стоит
   «подтверждено» в STATUS.md (геометрия окна, стекло, светофоры и т.д.).

6. **Отзыв Full Disk Access через реальный System Settings** (бриф явно это разрешает) — не
   стал делать: это интерактивное системное действие с диалогом подтверждения, у агента нет
   надёжного способа отозвать/вернуть его без риска не суметь восстановить прежде, чем закончится
   сессия. Вместо этого путь «БД недоступна» проверен через `dbPath` на несуществующий файл — это
   уже покрыто существующим тестом `StoreTests.testFailedRefreshDoesNotTouchExistingFile` и
   подтверждено читаемо: `refresh()` выходит по `throw` до `write()`.
